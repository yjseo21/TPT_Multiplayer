# TPT multiplayer: own-edit latency down to one round trip

**Engineering handoff, 2 November 2026.** Phase P2 of
`IN_GAME_MULTIPLAYER_PLAN.md`. Continues `SEAL_BATCHING_2026-11-02.md`; its
100 ms batching default is reversed here.

## Result

Own edit (sent by `--local-sim` client) to applied in that client's local world,
loopback, settled water/dust tray, one edit about every 0.7 s
(`tools/multiplayer/seal_batch_benchmark.py`, 30 s per row):

| `--seal-batch-ms` | Before p50 / p95 | **After p50 / p95** | Receive | Margin |
|---:|---:|---:|---:|---:|
| **0 (new default)** | 60 / 90 ms | **7.6 / 13 ms** | 0.051 Mbps | 2 ticks |
| 16 | 95 / 154 ms | 13.7 / 24 ms | 0.030 Mbps | 3 |
| 33 | 111 / 153 ms | 12.8 / 22 ms | 0.030 Mbps | 4 |
| 50 | 96 / 165 ms | 12.9 / 22 ms | 0.025 Mbps | 4 |
| 100 (old default) | 153 / 258 ms | 27.8 / 38 ms | 0.019 Mbps | 7 |

Every row ran at about 60 steps/s with 30 fingerprints verified and 0 resyncs.
RTT on loopback is about 0, so these numbers are pure overhead. Over a real
network expect about RTT + 8 ms.

## Why not lower: the round-trip floor

Without speculation, a client shows its own edit only once the server has
ordered it and said so: one round trip. Rollback speculation is ruled out by
measurement (`IN_GAME_MULTIPLAYER_PLAN.md` §1: 6–20 ms per physics step).
Scheduling edits ahead, or letting clients pick ticks, does not beat the
floor either, because the server's seals take one-way latency to reach
clients. The earlier plan claimed otherwise; that claim is corrected in the
plan. P3's ghost preview hides the round trip visually.

## Changes

**Server (`Room`, `Server.cpp`)**
- `Room::WaitForRequests(deadline)` / `Room::ApplyEarly()`: between ticks, the
  world thread waits on the request queue instead of sleeping. An edit applies
  at the current tick as soon as it arrives. Ordering is unchanged: edits at
  tick S always follow seal S and precede the step to S+1, whether `Step()` or
  `ApplyEarly()` applies them. Replay journals are identical.
- `--seal-batch-ms` default 0 (one seal per tick). Batching remains available.

**Client (`Session`, `ReplicaState`, `Client.cpp`)**
- Adaptive margin (`Session::Lead()`): the largest gap between seal advances
  over the last 3 s, in ticks, at least 1. Gaps that span a pause are ignored.
- Own-edit catch-up: while an own edit is in flight, the client steps up to 2
  ticks per frame toward the seal, never more, so heavy worlds cannot hitch.
- Measurement: `ReplicaState::committed` callback; `Session` matches commits by
  actor and sequence number. `tpt-remote --metrics` rows gain `editLatencyMs`
  (samples since the previous row), `editLatencySamples`, `editLatencyMeanMs`,
  `editLatencyMaxMs` and `paceLeadTicks`.

**Bug fixed (pre-existing, exposed by per-tick seals)**
- After a divergence, the server's `desync_detail` reply could arrive in the same
  network batch as further seals. The session ended the connection but kept
  processing the batch, found no local world, and treated it as a permanent
  failure instead of a resync (2 of 6 runs). `Session::Update` now stops
  processing a batch once the connection has failed. Afterwards: 10 of 10 runs
  passed.

**Tests**
- `multiplayer-local-client`: the four-player scenario runs with
  `--seal-batch-ms 50` (batching coverage) and asserts own-edit median latency
  under 100 ms with at least 2 samples. The divergence scenario uses the
  unbatched default. The running-ticks floor of the seal-ratio check was lowered
  from 60 to 30; it failed once at 59.
- `multiplayer-local-replica-network`: early application can apply several
  paused edits within one tick, so they share a seal. The paused case now runs
  6 s and checks edits, ticks and fingerprints instead of a seal count. The
  active case asks for 76 seals, since the initial seal sits at the join tick
  and 75 ticks need 76.

Full suite: 17 pass, 0 fail, 1 skip (impaired-network needs root). Windows
cross-build has no warnings, and the native unit tests pass. Cross-platform
harness, 3 minutes against the P2 server (per-tick seals, early apply): Linux
control 181 fingerprints, Windows replica 178, paced Windows client 178, 61
edits, 0 divergence, 0 resyncs.

## Not done

- Latency under real or emulated network delay (`tc netem` needs root here).
- Binary seal framing: bandwidth only, already about 0.05 Mbps.
- Video clients still see edits on the next server frame (`--update-rate`,
  20/s by default, so up to 50 ms).
